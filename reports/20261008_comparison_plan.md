## 0. 为什么要重新设计，而不是直接比较第14/15/16段

表里已明确三条限制，使**现有三段无法互为严格对照**：

1. 第14、15段**没有完整 TX 成功计数** → "我方发了"不是已验证条件。
2. 第14段**未覆盖电机断电/上电瞬间** → 不能断言"从上电起就没刷屏"。
3. 第16段**完整可比上电时序未记录**，且与第10、11段**签名不同**。

因此**不能**用"14/15 正常 vs 16 刷屏"直接推出"我方发送抑制刷屏"——这也是我此前撤回该结论的原因。方案必须重新采集可控数据。

## 1. 阶段一（先做）：单端纯监听 120 秒时序基线 —— 不发送、零风险

**要回答的问题**：仅电机上电时，它的状态是**稳定**的，还是**会自己变化**？

这一步必须先做，因为现有证据存在矛盾：

- 第10、11段：仅电机 → **100% 退化刷屏**（`0x232`）
- 第16段：仅电机 → **100% 退化刷屏**（`0x504`，**不同签名**）
- 第14、15段：仅电机 + 我方发送 → **正常业务报文，几乎无刷屏**

如果电机状态会自行在"正常"与"刷屏"之间跳变，那么第14/15段的"正常"**可能只是恰好落在正常窗口内**，与我方发送无关。**这个可能性必须先排除，否则 A/B 对照会把噪声当成因果。**

**方法**：
- 固件 `listen_1m`（只监听，不发送；状态行可证 `mode=listen`）
- 仅电机接总线；适配器单独供 5V；RS3 不参与
- **电机先断电** → 开始录制 → **电机上电** → **连续录 120 秒**
- 全程**不碰任何线**、不烧录、不按键

**判定**：

| 观察 | 结论 | 对后续的影响 |
|---|---|---|
| 120 秒全程刷屏、签名单一 | 电机单端状态**稳定** | 阶段二的 A/B 对照**有效** |
| 中途从刷屏变正常、或反复跳变 | 电机状态**会自行变化** | 阶段二必须改为"带时间戳的时序对照"，并记录跳变时刻；不能只比较"有没有刷屏" |
| 全程正常、无刷屏 | 第10/11/16段的刷屏**另有触发条件** | 需要先找出那个条件 |

**产出**：原始日志存 `captures/`（**进 Git**）、逐秒速率与签名表、上电时刻标记。

## 2. 阶段二：A/B 严格配对 —— 只改"我方发不发"这一个变量

前提：阶段一证明电机状态在 120 秒内**稳定**。若不稳定，先按阶段一的结论调整本阶段设计。

| | A 组 | B 组 |
|---|---|---|
| 固件 | `replay_s1_auto`（开机即发 `00:01`） | `listen_1m`（只监听） |
| 我方是否发送 | **是** | **否** |
| 电机起始状态 | **断电** | **断电** |
| 录制起点 | 固件开始发送之后 | 固件启动之后 |
| 录制中动作 | **给电机上电**（同一时刻标记） | **给电机上电**（同一时刻标记） |
| 时长 | 60 秒 | 60 秒 |
| 其余（模块、接线、适配器、终端） | 完全相同 | 完全相同 |

**关键控制**（吸取前面教训）：

1. **两组都不在录制期间烧录**——烧录会复位板子。先烧好、确认在跑，再开录。
2. **两组都显式记录电机上电时刻**（脚本每 5 秒打印计时，用户报"已上电"）。
3. **每组都保存完整原始日志 + 手工工况记录**（灯色、上电时刻、接线是否动过）。
4. **两组之间不改变任何接线**——只换固件。
5. **不用软件 RTS 复位**（此前因此把板子弄挂）；需要复位一律由用户按键或重新烧录。

**判定**：

| 结果 | 结论 |
|---|---|
| A 正常、B 刷屏 | **我方的 `00:01` 确实影响电机状态**（首次有对照支撑） |
| A、B 都正常 | 与我方发送无关；刷屏由别的条件触发 |
| A、B 都刷屏 | 同上，且说明单靠 `00:01` 不足以避免刷屏 |

## 3. 阶段三（仅在阶段二 A 正常时）：逐档增量

若 A 组证明 `00:01` 有效，再按 `reports/20261008_enable_set_plan.md` 的 S2→S5 逐档加报文，每档独立记录且**同样保留 A/B 式对照**（发 vs 不发）。

**目标终点**：电机指示灯从"红灯常亮（连接异常）"变为绿灯——这是 M3 的可判定成功标准（官方灯语见 AGENTS.md）。

## 4. 每段记录必须包含（缺一项该段即作废）

按 `AGENTS.md` 的抓包前置检查与表的建议：

1. 原始文件名 + SHA256（进 Git）
2. 北京时间、时长、完整帧数（以换行结束可解析的行）
3. 固件版本与环境名、`mode=` 状态行（证明发/不发）
4. **两端电源状态**（哪端通电、哪端物理不接）
5. **电机上电时刻**（相对录制起点的秒数）
6. **电机灯色 + 常亮/闪烁**（记录当时，不事后补）
7. 接线是否在本次前改动过
8. 发送侧计数（`sent=` / `rejected=`）——**表里正是指出前几段缺这个**，必须补上
9. 退化刷屏签名（CAN ID / DLC / payload）与出现时段
10. 显式区分"已知 / 候选 / 未知"

## 5. 重组口径（必须先固定，否则新数据与旧报告不可比）

`CAPTURE_FILE_MAP.md` 建议第 4 条要求"不将碰巧通过 CRC 的跨帧字节片段当成真实包"。本 agent 已实测两种口径的差异：

| 记录 | 按 CAN 帧边界重组（现行） | 旧 byte-scan | 差异 |
|---|---|---|---|
| `20261008_s1_verify.log`（新数据） | 7576 | 7576 | **+0** |
| `20261007_154729_002678_idle.log` | 4996 | 4998 | +2（0.04%） |
| `20261007_214348_391693_capture.log` | 7953 | 7965 | +12（0.15%） |

**即：新数据两种方法一致；旧报告的差异就是那 +2 / +12 个伪包。** 表中"典型上电包数 7965 与 7953 来自口径修订"得到实测确认。

**本方案一律以 `reconstruct_frames()`（按帧边界、整帧取用、不再扫描字节）为准**，并在每份新记录中同时给出 `complete` / `truncated` / `crc_fail` / `not_a_packet_start` 四项计数。

## 6. 本方案不做什么

- 不在 RS3 参与的总线上发送（安全边界不变）
- 不在录制期间烧录或复位
- 不把某一刷屏签名当作某设备的唯一指纹（表已验证至少三种签名）
- 不跨场景比较（表的建议第 3 条）
- 不自行接线；每段开始前由用户确认接线状态
