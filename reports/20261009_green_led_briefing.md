## 1. 审查结论

**原简报把两种不同配置的自收日志当成同配置对照，因而“已经找到不绿根因”的结论不成立。** 现有证据确实显示 `replay_echo` 的记录只有 `00:01` 首片，却不能直接归因于 `replay_bisect5`，更不能据此断言电机不 ACK。

- `replay_bisect5`：当前源码、`TX_QUEUE_LEN=8`、`REPLAY_LEGACY_SEND=1`、没有自收。
- `replay_echo`：当前源码、**`TX_QUEUE_LEN=0`**、`REPLAY_LEGACY_SEND=1`、`REPLAY_ECHO_FRAMES=1`。
- `replay_hist_echo`：历史源码、**发送队列写死为 8**、`REPLAY_ECHO_FRAMES=1`。

自收实验同时改变了发送队列和源码；原表中的 `bisect5` 必须改读为 `replay_echo`。原始文件没有旁边的同名采集 `.json`，也没有记录实际 TX 队列配置的启动行；环境关联来自历史交接与当前配置，并非日志独立证明。

## 2. 两个应优先处理的代码问题

**分片发送空闲检查的位置错误。** `src/transmit_replay.cpp` 的 `send_packet()` 只在整包进入时检查一次 `msgs_to_tx`，随后立即调用两次或三次 `twai_transmit()`。队列为 0 时，首片尚未完成，第二片会立即被拒；20 ms 参数只等待队列空间，不会在禁用队列时等待硬件空闲。`REPLAY_LEGACY_SEND=1` 又跳过了唯一的空闲检查。因此无需假设“不 ACK”，代码本身就能产生首片有、尾片无的现象。下一步应在**每个分片提交前**有界等待空闲，并在超时/驱动状态异常时停止，保留 `TX_QUEUE_LEN=0`。

**驱动卸载没有与收包任务同步。** 当前与历史回放源码在 `receive_task()` 调用 `twai_receive(...,20ms)` 时，另一核的 `set_mode()` 可以直接 `twai_stop()` / `twai_driver_uninstall()`。自动启动时先创建收包任务再切换模式，窗口结束也再次卸载，存在删除仍有任务阻塞的 RX 队列的风险。官方要求卸载前没有任务阻塞在 TX/RX 队列或 alerts。应先让收包任务退出驱动调用并确认，再卸载/重装。`src/main.cpp` 的原子标志也不能单独保证已经进入的调用结束，不能照搬成完整修复。

原先“任务 xQueueSend 与 ISR xQueueReceiveFromISR 竞争，所以 IDF 必然损坏队列”的根因说明**未被证明**；这两种 API 本就是队列的任务/ISR 使用方式。保留非零队列关联崩溃、零队列改善稳定性的实测记录及禁用队列规避，不把它们升级为已定位的 IDF 缺陷。驱动生命周期风险是另一个需修复的具体候选，尚未用硬件证明它解释所有 panic。

机制已核对本机 Arduino core 的 IDF 版本头（4.4.7）、本机 `driver/twai.h` 与 [Espressif v4.4.7 TWAI 文档](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/peripherals/twai.html)及[对应驱动源码](https://github.com/espressif/esp-idf/blob/v4.4.7/components/driver/twai.c)。

## 4. 协议与硬件事实的范围

- `00:01` 请求：CAN `0x503`，13 B = **8+5**；`55 0D 04 33 E5 BF 00 00` + `40 00 01 DD FE`。
- `04:69` 稳态零值模板：CAN `0x503`，19 B = **8+8+3**；`55 13 04 03 E5 BF 00 00 00 04 69 0F 04 08 19 00 00 6B 56`。
- CRC8 init `0x77` / poly `0x8C`；CRC16 init `0x3692` / poly `0x8408`。末尾候选值的语义、符号与量纲仍未验证。
- 项目配置：ESP32-S3 DevKitC-1、GPIO4 TX / GPIO5 RX、1 Mbps；串口号、当前固件、板子状态和接线必须使用前核实，不继承旧 COM17。
- 当前两版源码在跳过启动消息时**都是先调用 `00:01`，再调用 `04:69`**；原“发送顺序不同”猜测与源码不符。
